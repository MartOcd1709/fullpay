# Production-shaped quality bar: what a technical judge checks in a 48-hour build, and what FullPay does about each

**Status:** research and design only (Day 0, Fri 23 Oct 2026). No application code. Builds on `10_build_plan.md` Rev F.1, `lld.html` Rev B, `13_reference_library.md` and `14_build_checklist.md`. Items already pinned there are marked **(plan)** and are not re-proposed; only the delta is costed. Costs assume one strong developer pairing with Claude. Sources are linked inline; the list at the end repeats them.

## 0. How a technical judge spends ten minutes on our four links

Six judges score asynchronously from the GitHub repo, the live URL, a ≤3-minute video and a deck. The technical judge opens the repo first: README above the fold (what it is, live link, video), the file tree, `tests/`, the CI badge, the last twenty commits, `.env.example`. Then the live URL with DevTools open: log in, click three screens, refresh a deep link, open `/api/health`, glance at response headers, run Lighthouse from the DevTools panel. Everything below is designed to be visible inside that window. The stance is the plan's own: production-*shaped* (real database, migrations, auth boundary, transactions, idempotent jobs, tests, deployed, documented), never production-*scale*, with the gap stated before the judge finds it.

Grep of the design set confirms the plan already covers tests, CI, health, the error envelope, empty states, idempotency, migrations, seed, login rate limiting, axe and Lighthouse. It has **nothing on security headers, structured logging, request ids, Next.js error/loading/not-found conventions, `preDeployCommand`, `RENDER_GIT_COMMIT`, fonts, manifest, favicon, `lang` switching or `noindex`**. Those are the main additions.

**Plan has:** node:test suites for gst, interest, chain, ladder, recon, forecast, time (LLD §12, ~50 tests), GH Actions `node --test` on every push (P1.10), one Playwright e2e.

### 1.3 The error contract

**Judge checks:** bad input to any API → same JSON shape, right status, no stack trace, no `Cannot read properties of undefined`; unknown `/api/*` path → JSON 404; a thrown error → generic message with an id; the UI shows words, not `[object Object]`.

**Plan has:** `{error:{code,message}}` as a global invariant; 401 login; 404/410 token semantics; 409 tick lock; owner routes re-check the cookie.

**Do (delta):**
- Freeze the status → code table in the README API section and in one `lib/http.js`: 400 `VALIDATION` (+ `fields: {amount_paise: "must be a whole number of paise"}`), 401 `UNAUTHENTICATED`, 403 `FORBIDDEN` (wrong machine secret), 404 `NOT_FOUND`, 409 `CONFLICT` (tick lock, state conflicts such as sending a paid invoice, duplicate send), 410 `TOKEN_EXPIRED`, 413 `PAYLOAD_TOO_LARGE`, 429 `RATE_LIMITED` (+ `Retry-After`), 500 `INTERNAL` (+ `request_id` only).
- `lib/http.js` ≈ 30 lines: `route(fn)` wraps every handler (`export const POST = route(async (req, ctx) => …)`): try/catch, `AppError(code, status, message, fields?)`, unknown errors logged with `request_id` and returned as `INTERNAL`, `Cache-Control: no-store` and `x-request-id` on every API response.
- Server returns English `message` + stable `code`; the UI maps `code` → i18n key (`errors.VALIDATION`), so Hindi stays complete without the server knowing the language.
- `app/api/[...rest]/route.js` returns the JSON 404 so unknown API paths never render the HTML not-found page (5 min).
- State in README that the envelope is deliberately smaller than [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457) (`application/problem+json`, `type/title/status/detail/instance`) and that RFC 9457 is the production upgrade: shows the team knows the standard and chose simplicity.
- Next.js strips server error messages in production and exposes `error.digest`; the error boundary should show "Reference: <digest>" so a server log line can be matched ([error.js](https://nextjs.org/docs/app/api-reference/file-conventions/error)).

**Cost:** 30 min at Sat 12–3 AM when the first routes are written; near zero if done first, expensive to retrofit.

### 1.4 Input validation at the boundaries

**Boundaries:** (a) owner JSON APIs (authenticated, still validated); (b) public `/api/pay/:token/*` (hostile internet); (c) CSV import; (d) URL params and query filters; (e) config PATCH; (f) machine endpoints (`/api/tick`, `/api/reseed`); (g) outbound encodings (email HTML, CSV export, UPI string, wa.me text).

**Judge checks:** `amount_paise: 1.5`, `-1`, `"abc"`, `2^60`; a GSTIN with a wrong check digit; `31/02/2026`; an unknown enum; a 10 MB body; `token=../`; `hash=<script>`; `' OR 1=1` in search. Expects 400 with field names, never 500.

**Plan has:** GSTIN mod-36 validation, `asPaise()` guarding 2^53, enum statuses, `skipped[]` reporting for CSV, `timingSafeEqual` secrets, CSV-injection-safe export, URL-encoded UPI params.

**Do (delta), no new dependency (the ladder: stdlib before a schema library):**
- `lib/validate.js` ≈ 60 lines: `obj(body, schema)` where each schema value is a small validator: `int({min,max})`, `paise()` (safe integer ≥ 0 via `asPaise`), `date()` (`^\d{4}-\d{2}-\d{2}$` plus a real-calendar check through `lib/time.js`), `str({max})` (trim, length, strip control characters), `oneOf([...])`, `gstin()`, `email()`, `phone()` (`^\+91[6-9]\d{9}$`), `vpa()`, `ifsc()` (`^[A-Z]{4}0[A-Z0-9]{6}$`), `pin()` (`^[1-9][0-9]{5}$`), `optional()`. Throws `AppError('VALIDATION', 400, …, {fields})`. One test file with ~15 cases.
- Body cap inside `route()`: `content-length` > 1,000,000 → 413 before `req.json()`; CSV import 1 MB, 5,000 rows, 512 chars per cell, strip the UTF-8 BOM. Next.js recommends a reverse proxy for payload limits when self-hosting ([self-hosting](https://nextjs.org/docs/app/guides/self-hosting)); Render's load balancer fronts us but its body limit is undocumented, so the app enforces its own.
- Param regexes before any DB call: token `^[A-Za-z0-9_-]{20,32}$` (base64url of 16 bytes = 22 chars), hash `^[0-9a-f]{64}$`, ids `^\d{1,12}$`, FY `^\d{2}-\d{2}$`. Cheap 404/400 and no enumeration leaks.
- Lists: parameterised SQL only (`$1`), `ILIKE` with escaped `%` and `_`, `LIMIT 200`.
- Config PATCH: allow-list of keys; ladder offsets integers in [-30, 365] and strictly increasing; buffer ≥ 0; sourced legal values (RBI series, GST slabs, TDS) are not editable from the UI, only from `config` with a `source` and `verified` date.
- Reference: [OWASP Input Validation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)†.

**Cost:** 45 min (Dev A, Sat 12–3 AM) plus validators growing with routes.

### 1.5 Empty, loading and error states

**Judge checks:** after "Reset demo" with a fresh DB, every screen has a designed empty state; a slow network shows skeletons, not a blank; a thrown error shows a branded page with retry (the pack's own Debug prompt asks for "a simple error screen, so a crash in one screen shows a message instead of a blank page"); an unknown URL shows a branded 404; an expired pay token shows a friendly page in the customer's language.

**Plan has:** one i18n-keyed empty state per screen (LLD §10), P7.5, token 404/410 semantics.

**Do (delta) with Next.js file conventions, five files:**
- `app/(owner)/loading.js`: one shared skeleton (three stat tiles + list rows) wrapped automatically in Suspense; extra `loading.js` for forecast and payments ([loading.js](https://nextjs.org/docs/app/api-reference/file-conventions/loading)). Caveat from the docs: if the **layout** reads `cookies()` or uncached data, the fallback will not show; keep the cookie check in `proxy.js`, not in the layout.
- `app/(owner)/error.js` (`'use client'`): plain-words message, "Try again" calling `retry ?? reset` (`retry` is stable from 16.3.0; destructure both), "Reference: <digest>", `console.error` of the error ([error.js](https://nextjs.org/docs/app/api-reference/file-conventions/error)).
- `app/global-error.js`: own `<html>`/`<body>`, no theme dependencies (root-layout failures).
- `app/not-found.js`: branded EN/HI 404 with a link home; the root file also handles every unmatched URL (since 13.3). Do not use `global-not-found.js`; it is experimental ([not-found.js](https://nextjs.org/docs/app/api-reference/file-conventions/not-found)).
- `app/pay/[token]/not-found.js` plus an explicit "link expired" view. Call `notFound()` before any Suspense boundary so the response really is a 404 (after streaming starts the status stays 200 with a `noindex` meta).
- Copy rule for every state: what happened, what to do next, a reference id; never the raw message.

**Cost:** 20 min for the files + 10 min EN/HI copy (Dev B, Sun 9–12 or earlier).

### 1.6 Idempotency

**Plan has (strong):** outbox with `Idempotency-Key: outbox-<id>-<attempt>` and Resend's 24-hour window; CSV `dedupe_hash`; tick in one transaction under `pg_try_advisory_xact_lock(7)` with CAS rung transitions and max one rung per invoice per tick; `UNIQUE(fy, seq)`; partial unique `one_open_promise`; deterministic reseed.

**Judge checks: the six double-submits.** (1) Double-click **Send** on a new invoice → one number, one `invoice_sent` event. (2) Customer double-taps "I've already paid" → one claim. (3) `/api/tick` twice in a minute (a cron retry) → second call returns 200 `{advanced:0}` when sequential, 409 when concurrent, and no second email. (4) Same CSV imported twice → 0 new rows. (5) Retry `/api/outbox/:id/send` after a timeout → Resend dedupes. (6) Demo-clock "advance" pressed twice → same date, no double rung.

**Do (delta):** encode all six as acceptance rows (two as `tests/db`); for (1) use `UPDATE invoices SET status='sent', seq=… WHERE id=$1 AND status='draft'` and, on zero rows, return the already-sent invoice with 200 (retry-safe rather than 409); for (2) a partial unique index `one_open_claim ON payments(invoice_id) WHERE source='claim' AND confirmed_at IS NULL`, returning the existing claim. Note in README that the outbox follows the semantics of the IETF `Idempotency-Key` draft (draft-08, 22 Oct 2026: same key + different payload → 422, concurrent → 409) and that accepting client keys on owner POSTs is a production step ([Idempotency-Key draft](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)).

**Cost:** 30 min tests + 10 min CAS tweaks.

### 1.7 Migrations and seed

**Judge checks:** can they run it locally in under five minutes; is the migration applied automatically on deploy; does the seed reproduce the README's numbers; is there a migrations record.

**Plan has:** `db/schema.sql` as the day-zero migration applied idempotently twice (P1.3), deterministic `db/seed.js` with the pinned `INV/26-27/0042` hash (P1.9), `/api/reseed` replying 202 then working, nightly reseed.

**Do (delta):**
- `db/migrations/001_init.sql` + `db/migrate.js` (≈20 lines): apply files in order inside a transaction, record `schema_migrations(name, sha256, applied_at)`, skip applied ones; statements stay idempotent (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`, `DROP TRIGGER IF EXISTS` then `CREATE TRIGGER`) ([PostgreSQL CREATE TABLE](https://www.postgresql.org/docs/current/sql-createtable.html)†). Weekend schema changes become `002_*.sql`; never edit `001` after the first deploy.
- `render.yaml`: `preDeployCommand: npm run db:migrate`. Render runs it after the build and before the new instance starts, on paid web services (Starter qualifies), with a 30-minute timeout; if it fails the deploy fails and the previous version keeps serving ([Render deploys](https://render.com/docs/deploys)). If the first deploy is on Free, run `npm run db:migrate` by hand.
- Local: `node --env-file=.env db/migrate.js`; `npm run db:reset` = migrate + seed, refusing to run when `RENDER=true` unless `DEMO_MODE` ([Render env vars](https://render.com/docs/environment-variables)).
- `db/seed.js` prints and asserts a summary (customers 14, invoices by status, outbox 0, the pinned hash, DSO 58 d); the README quotes that printout.

**Cost:** 20 min Fri.

### 1.8 Health endpoint

**Plan has:** `GET /api/health → {ok:true}` public; `lastTick`/db detail behind the secret header; `healthCheckPath: /api/health`; cron-job.org keep-alive.

**Do (delta):** return `{status:"pass", service:"fullpay", version:"<RENDER_GIT_COMMIT, 7 chars>", node:"v22.x", time:"…", uptime_s:n}` with `Cache-Control: no-store`. The `status/version/releaseId` fields follow the (expired but widely used) [health+json draft](https://datatracker.ietf.org/doc/html/draft-inadarei-api-health-check-06). **No DB call on the public path**: Render restarts an instance after 60 s of failed checks, so a database blip must not restart the web service; `?deep=1` with the secret adds `checks.db` (ms), `last_tick` (run id, time), `outbox` (queued, failed). Render treats any 2xx/3xx within 5 s as healthy, moves traffic to a new instance only when it passes, and cancels a deploy that never passes within 15 minutes ([Render health checks](https://render.com/docs/health-checks)). `RENDER_GIT_COMMIT` is set at build and run time ([Render env vars](https://render.com/docs/environment-variables)). README line: "Open /api/health; `version` equals the latest commit on `main`", the proof that we deploy what we show.

**Cost:** 15 min.

### 1.9 Logging without PII

**Judge checks:** `grep -rn "console.log" app lib`; are bodies, emails, phones, tokens logged; is there a request id; can an error page's reference be matched to a server line.

**Plan has:** "no PII in logs" as a trust-layer rule; `/verify` returns no PII; events carry canonical payloads.

**Do (delta):**
- `lib/log.js` ≈ 20 lines: `log.info|warn|error(msg, fields)` → one JSON line on stdout `{ts, level, msg, req_id, …fields}` (12-factor: logs are an event stream to stdout, [12factor](https://12factor.net/logs)†). A denylist of keys (`email, phone, name, address, body, text, subject, password, token, pay_token, secret, authorization, cookie, vpa, account, ifsc, gstin`) **throws in test and redacts in production**; ids and paise amounts are allowed. `ts` comes from `time.nowIso()` so the LLD's `new Date` grep gate stays clean.
- `req_id = req.headers.get('rndr-id') ?? crypto.randomUUID()`, echoed as `x-request-id` and inside 500 bodies. Render's HTTP request log entries carry a `requestID` that matches the `Rndr-Id` header, so one id joins our line with Render's ([Render logging](https://render.com/docs/logging)).
- `tests/unit/log.test.js`: `log.info('x', {email:'a@b'})` throws. This is the proof judges like: "no PII in logs, enforced by a test".
- Volume: Render drops lines above 6,000 per minute per instance and keeps Hobby logs 7 days; the tick logs one summary per run and one line per send, never one per invoice evaluated ([Render logging](https://render.com/docs/logging)). Render's explorer filters on a `level` field.
- Gate: no `console.log(` outside `lib/log.js` (`console.error` allowed in `error.js`).

**Cost:** 20 min.

### 1.10 Security headers and login rate limiting

**Plan has:** `proxy.js` allow-list, HMAC-signed httpOnly cookie, `OWNER_PASSWORD` compared with `timingSafeEqual`, 5 attempts/min/IP in an in-memory Map, cookie re-checked in every owner route (CVE-2025-29927), 16-byte expiring pay tokens, 10/min/token on claims, no secrets in any response, CSV-injection-safe export. **Nothing on response headers.**

**Judge checks:** `curl -I` → HSTS, `X-Content-Type-Options`, frame protection, `Referrer-Policy`, `Permissions-Policy`, a CSP, no `X-Powered-By`; a securityheaders.com grade; brute-forcing `/api/login` → 429; cookie flags; logout.

**Do (delta), 15 minutes in `next.config.js`:**
- `poweredByHeader: false` ([poweredByHeader](https://nextjs.org/docs/app/api-reference/config/next-config-js/poweredByHeader)†).
- `headers()` for `/(.*)` ([Next.js headers](https://nextjs.org/docs/app/api-reference/config/next-config-js/headers), values per [OWASP HTTP Headers Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html)): `Strict-Transport-Security: max-age=63072000; includeSubDomains` (Render redirects HTTP→HTTPS and manages TLS but its docs do not mention HSTS, so the app sends it; omit `preload` unless the domain is submitted) ([Render TLS](https://render.com/docs/tls)); `X-Content-Type-Options: nosniff`; `Referrer-Policy: strict-origin-when-cross-origin`; `Permissions-Policy: camera=(), microphone=(), geolocation=()` (a future `<input type=file capture>` for photo intake is unaffected); `X-Frame-Options: DENY`; `Content-Security-Policy: frame-ancestors 'none'; object-src 'none'; base-uri 'self'; form-action 'self'; upgrade-insecure-requests`. Deliberately **no `script-src`**: a strict CSP needs per-request nonces, which force dynamic rendering of every page; Next.js documents that as the production path ([Next.js CSP guide](https://nextjs.org/docs/app/guides/content-security-policy)). Say so in path-to-production.
- `X-Robots-Tag: noindex` for `/pay/:path*`, `/print/:path*`, `/api/:path*` (customers' invoices must never be indexed; also a DPDP minimisation point). Dynamic pages already get `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` from Next.js ([self-hosting](https://nextjs.org/docs/app/guides/self-hosting)); `route()` sets `no-store` on APIs explicitly.
- Verify with `curl -sI https://<url>` and a [securityheaders.com](https://securityheaders.com)† scan (expect A; A+ needs the full CSP); screenshot to `docs/`.
- Login (10 min on top of the plan): derive the client IP from the first `x-forwarded-for` hop (behind Render's load balancer every judge would otherwise share one IP) ([Render web services](https://render.com/docs/web-services)); add a per-account counter (10/min total) beside the per-IP one; 429 with `Retry-After: 60`; generic "Password incorrect"; `log.warn('login_failed', {ip_hash})`; cookie `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=43200`; `POST /api/logout`. The Map resets on deploy; state it in path-to-production.
- GitHub side (no code): secret scanning runs automatically and free on public repositories ([about secret scanning](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning)); user-level push protection is on by default and bypassable, repository-level is **off by default** and should be switched on in Settings → Code security on Day 0 ([push protection](https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection)). `.env` in `.gitignore` in commit 1. Skip Dependabot *version updates*: they open PRs on the frozen repo during judging week ([Dependabot config](https://docs.github.com/en/code-security/dependabot/dependabot-version-updates/configuring-dependabot-version-updates)); alerts are enough. Run `npm audit --omit=dev` once before freeze.

### 1.11 Accessibility (axe) and Lighthouse targets

**Plan has:** pack design rules (16 px body, 48 px buttons, AA contrast, visible focus, labels, icon + word on statuses), UX4G tokens, P7.7 axe with 0 serious issues on three screens, P7.8 Lighthouse accessibility ≥ 90.

**Judge checks:** DevTools → Lighthouse on the dashboard while logged in; keyboard-only run through New invoice; icon buttons with names; contrast; `lang`; 360 px.

**Targets (deployed URL, incognito, mobile preset):** Accessibility ≥ 95 and Best Practices ≥ 95 on dashboard, invoices, new invoice, follow-ups, `/pay/:token`; Performance ≥ 75 mobile / ≥ 90 desktop on the dashboard and ≥ 90 mobile on `/pay/:token`; SEO not applicable (noindex pages). Lighthouse's bands are 0–49 red, 50–89 orange, 90–100 green; performance weights are FCP 10 %, SI 10 %, LCP 25 %, TBT 30 %, CLS 25 %; scores vary run to run, so record the median of three ([performance scoring](https://developer.chrome.com/docs/lighthouse/performance/performance-scoring)). The accessibility score is a weighted pass/fail of axe-core rules; manual checks (focus order, keyboard traps) are not scored, so the keyboard pass is still required ([accessibility scoring](https://developer.chrome.com/docs/lighthouse/accessibility/scoring)).

### 1.12 Performance on a Render Starter instance

**Do:**
- **Region: Singapore** for web, Postgres, cron and Workflow (closest to Indian judges; the choice is permanent, so P0.2 today).
- Server components read through `lib/*` and `db.js` directly; never `fetch(APP_URL + '/api/…')` from the server (double hop, double JSON on 0.5 CPU) ([fetching data](https://nextjs.org/docs/app/getting-started/fetching-data)†). API routes serve client mutations and machine calls.

- Pool `max: 5`, `idleTimeoutMillis: 10000`, `connectionTimeoutMillis: 5000`, internal connection string (same region).

## Risks

- **Hydration mismatch from dates and money formatted on a UTC server and re-rendered in an IST browser** (L: High, I: Red console errors on every screen, failing the pack's 'no console errors' check and making the app look broken in DevTools.) — All dates and money are formatted only in lib/time.js and lib/money.js (string in, string out), rendered in server components or passed as preformatted strings; no `new Date` in components (LLD grep gate); set TZ=Asia/Kolkata on Render as belt-and-braces; check the console on every screen during the Sunday sweep.
- **The judging platform embeds the live URL in an iframe and the new frame-ancestors 'none' header shows a blank frame** (L: Low to medium, I: Judges see an empty preview and may not click through to the real URL.) — Default to `frame-ancestors 'none'` and X-Frame-Options DENY (OWASP), but if the platform iframes submissions, switch to `frame-ancestors 'self' https://<platform-origin>` and drop X-Frame-Options.
- **preDeployCommand does not run because the first deploy is on a Free instance** (L: Medium, I: Schema missing on the live URL; every page 500s until someone runs the migration by hand.) — Create the web service on Starter from the first deploy (covered by the participant credit); keep `npm run db:migrate` runnable by hand and make the health deep check report the applied migration count.
- **Render region chosen in the US on Day 0 cannot be changed later** (L: Medium, I: Every judge in India pays 200+ ms extra per request; dashboard TTFB and Lighthouse performance drop; migrating means recreating the database.) — Create the Postgres today in Singapore and every later service (web, cron, Workflow) in the same region so the internal connection string and private network work.
- **A real secret (Resend key, OWNER_PASSWORD, DATABASE_URL) lands in a commit at 2 AM** (L: Medium, I: Public repo leaks credentials; rotation mid-event and a visible 'remove secret' commit in the history judges read.) — .env in .gitignore in commit 1; `npm run gates` greps for key prefixes; user-level push protection is on by default but bypassable, so enable repository-level push protection; rotate all demo keys after the event (plan).
- **Lighthouse performance scores on Starter come out orange (50–89) on mobile** (L: Medium, I: A judge who runs Lighthouse sees an orange performance number next to green accessibility and best-practices scores.) — Set honest targets (≥75 mobile, ≥90 desktop for the dynamic dashboard; ≥90 mobile on /pay), load recharts dynamically, self-host fonts via next/font, query the DB directly from server components, record the median of three runs and publish the dated reports; lead with Accessibility and Best Practices in the deck.
- **Playwright in CI adds minutes and flakiness and turns the badge red at the wrong moment** (L: Medium, I: A red badge on the frozen repo during judging week for a browser download timeout, not a product bug.) — Keep the single e2e local and in the Sunday rehearsal; if it goes into CI, make it a separate job with continue-on-error so the unit/db job owns the badge.
- **Tick logging per invoice exceeds Render's 6,000 lines/min/instance and drops the lines the deck needs** (L: Low, I: The 'autonomy proof' screenshot of the workflow run log is incomplete or missing the send lines.) — Log one summary line per tick run (run_id, evaluated, advanced, queued, sent) and one line per send; never per invoice evaluated; capture the screenshot during the Sat 11 PM checkpoint.
- **A Next.js version below 16.3 lacks the stable `retry` prop in error.js** (L: Low, I: Error boundary's Try again button is undefined; a judge who triggers an error cannot recover without reload.) — Destructure `{ error, retry, reset }` and call `(retry ?? reset)()`; pin the Next.js version in package-lock.
- **The loading skeleton never shows because the owner layout reads cookies()** (L: Medium, I: Navigation blocks until the whole page renders; screens feel slow in the video and the loading.js files look like dead code.) — Keep the cookie check in proxy.js and in route handlers (plan); do not call cookies() or uncached data in app/(owner)/layout.js; fetch inside page.js under the Suspense boundary.
- **Node version drift between laptop, CI and Render** (L: Low, I: A test passes locally on Node 24 and fails on Render's Node 22 build (or vice versa), e.g. a flag considered experimental on one line.) — One `.node-version` file read by Render (second in precedence after NODE_VERSION) and by setup-node (`node-version-file`); `engines.node` with an upper bound; both devs install the same line with their version manager.
